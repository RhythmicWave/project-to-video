# 简历与面试视角

## 简历稿：把实现提炼成有依据的承诺

先理解项目，再写简历。格式为项目名、一句总述和 3–4 条要点。总述交代服务谁、解决什么问题、项目的核心形态；要点选择相互补充的贡献或设计，避免罗列技术名词。

每条按“做了什么 + 用了什么关键技术/机制 + 解决的难题或验证过的范围/结果”组织。例如可写“实现……，通过……处理……，支持……”，但具体名词和结果必须来自本项目证据。

结果可以是明确的能力边界，如支持何种输入、如何处理失败、实现何种隔离；不要求每条都填性能百分比。量化指标需有测量条件和来源。个人负责范围只能根据用户说明或可靠贡献记录确定，不能从代码量猜测。

resume.md 中先放可复制的简历正文，再用短附注关联证据 ID 和待确认的个人贡献。推断、未实现计划和目标指标不能混入已完成能力。

## 独立面试官：先看承诺，再提追问

支持干净上下文时，新建独立 Agent，关闭历史继承（例如工具的 `fork_turns: "none"`）。只有该能力实际存在时才使用相应参数，不假设所有宿主提供同一工具。

可以采用以下任务输入，并替换简历正文与已知岗位信息：

```text
你是技术面试官，仅依据下面的简历项目介绍提出追问。
请指出每个问题对应的简历承诺、为什么值得问，并给出一个有区分度的后续追问。
问题覆盖整体架构、核心链路、关键设计取舍以及会改变结果的边界条件。
保持精炼，合并重复问题；不要给答案，不假定项目具有简历之外的能力，不读取源码。
岗位/级别：仅填写用户已明确提供的信息；未知时按一般项目深挖处理。
简历正文：……
```

通常约 6–10 个主问题即可形成有用检查；依项目规模调整，不追求数量。不能创建独立 Agent 时由主 Agent 进行角色审阅，注明“未隔离上下文”，仍完成同样产物。

## 将问题转成重点，不转成分镜目录

主 Agent 对照源码整理问题，区分：解释主干机制所必需、局部实现细节、超出现有能力/信息不足。修正不实的简历承诺；保留有效的边界追问，并说明实现实际如何处理。

选择展示重点时，同时考虑该机制在项目中的中心性、理解难度、动态可视化收益及简历承诺。只有覆盖检查发现主线中的关键因果缺失时，才补动画；源码分支、数据结构细节或环境限制一般放笔记。

例如，“请求如何完成”“失败如何返回”“状态在哪里保存”可能都由同一条请求生命周期解释。将它们关联到该生命周期的实际片段，不据此制作三个彼此割裂的问答章节。

最终检查回答是否能说清“发生了什么、为什么、何时不成立”，而不只是能背出一个组件名。
