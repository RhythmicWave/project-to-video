# 项目探索、主线选择与非线性讲解

项目复习动画的难点通常不是把模块画出来，而是从源码中找出一条能解释系统的因果主线，并决定哪些细节必须进入画面。先建立“可讲解模型”，再写分镜和组件；不要从画布或图标开始。

## 按缺口深入探索

下面是五个检查视角，可以合并或跳过已经核实的部分；不要求把同一份源码读五遍。用户指定的文档、现有简历和有效调研优先复用，先补会改变主线理解的缺口。

### 边界地图

只回答系统由哪些运行边界组成：进程、线程/任务、客户端、外部服务、主要存储、协议入口和状态所有者。记录“谁调用谁”“谁观察谁”“谁保存谁产生的数据”，不要把目录结构直接当架构图。

完成条件是能说明一次请求跨越哪些边界，以及每个边界之外有什么。边界不清时，先读启动入口、依赖注册、协议模型和运行配置。

用户指定文档可作为主要导航，不要求重建文档目录。对关键关系再检查启动接线：区分当前入口接入的实现、未接线变体、仅在测试中装配的方案和演进建议。类型或方法存在，不证明读请求会经过它；心跳存在，也不证明过期任务已实现接管。调研记录标出区别，分镜在影响结论的位置用简短方案标签或分支表达。

### 任务清单

从用户可感知的任务或系统触发点列出 3–5 条候选流程，例如提交请求、读取数据、审批工具、恢复任务、回放记录。候选流程必须有触发和结束，不以“某个模块”作为流程名。

优先挑一条正常路径，再挑一条会改变理解的分支：拒绝、失败、等待恢复、重试、压缩、回放或并发汇合。小项目可以只有一条，但仍要检查至少一个重要边界条件。

### 端到端追踪

对每条候选流程记录：

    触发 → 输入/关联 ID → 关键调用 → 状态变化 → 可见后果
         → 结果去向 → 持久化或下一次入口 → 条件分支

遇到异步调用，继续追踪 Future、回调、事件订阅或任务句柄的恢复者；遇到存储，分别确认写入者、读取者和读取时机；遇到事件，区分发布、订阅、推送、落盘和回放。不要以“发出事件”作为流程终点。

每个主流程确认生产实现，并查看现有相关测试或协议断言；没有对应测试时使用源码证据并记录范围。不能把测试文件名当作行为证据，也不为制作视频补无关业务测试。

### 横切机制回挂主线

单独盘点权限、事件、日志/Trace、配置、重试、缓存、压缩、插件和扩展。只有当它改变主线的状态、结果、可见性或下一步时，才在视频中展开；否则在主线经过它的位置挂一个短注释并放进笔记。

横切机制必须接回一个具体动作。例如“EventBus”要说明它把哪类变化送给谁；“Trace”要说明记录来源、字段和写入去向；“缓存”要说明命中时跳过什么。

### 证据与疑点

为每个重要结论登记源码符号、测试范围、执行验证或推断等级。默认以当前实现及接线为事实；用户明确要求采用文档指正结果时，使用修正后的讲解基准，内部保存实现差异。未接入的变体、演进设计和已实现能力分别标清。无法确认的关系移入疑点记录，不画成确定的主链路。

算法或协调设计与实现不符时，按本次讲解基准表现不变量与边界；只有用户需要理解该差异时才将它展开成镜头。响应成功、入队、持久化、去重、位点推进、租约和业务副作用分别核查，避免把局部原子性扩大为跨系统的恰好一次保证。

## 从候选流程选主线

先写一句系统核心承诺，例如“一个任务如何进入系统、经过决策和执行，最后留下可继续工作的结果”。再把候选流程按以下维度做 0–3 的相对评分：

| 维度 | 需要问的问题 |
| --- | --- |
| 中心性 | 不理解它，是否无法理解项目的主要价值？ |
| 因果难度 | 是否包含容易混淆的边界、状态或时序？ |
| 设计价值 | 是否体现项目的关键取舍或工程难题？ |
| 动态收益 | 状态、数据或角色变化是否值得用动画展示？ |
| 证据强度 | 是否能从源码和测试形成闭环？ |
| 讲解成本 | 是否需要大量前置概念才能讲清？成本越高分越低。 |

选出一条“锚点主线”和最多两条支撑线。支撑线必须回答锚点主线中的具体疑问，例如“审批如何恢复等待”“结果如何写入”“上下文为何改变”；不能只是因为某个模块很有趣就插入。面试问题只用于检查覆盖，不用于决定流程数量。

## 深度是否足够

主线的每个关键阶段按三层判断是否展开：

1. 定位层：观众知道当前在哪个边界、谁参与、输入从哪里来。
2. 因果层：观众看到哪个动作改变了什么状态，以及后果如何进入下一步。
3. 边界层：观众知道等待、失败、拒绝、并发、持久化或恢复何时会改变结论。

主链路至少完整覆盖定位层和因果层；只要某个边界会改变面试回答或系统结果，就补边界层。可以省略低频实现细节，但不能省略关联 ID、恢复者、写入/读取时机、选择结果或分支后果这类“看似小、实际改变结论”的信息。

一种实用分配是：主线完整展开，支撑机制只展开一个闭环，低频细节放笔记。不要用固定秒数或固定节点数硬套所有项目；当观众无法回答“谁触发、谁持有状态、数据去哪、失败后怎样继续”时，说明省略过度。

具体的全景、子流程和机制镜头如何取舍技术细节，统一见[讲解质量](explanation-quality.md)。跨多份文档时先把共享参与者、数据和完成边界合并成系统模型，再按学习问题编排；文档章节用于回查，不直接成为视频章节。

## 选择叙事顺序，而不是按文件顺序讲

视频可以不按源码调用顺序呈现，但事实和运行顺序必须在画面或笔记中明确。可选的叙事结构包括：

| 结构 | 适合解释 | 关键约束 |
| --- | --- | --- |
| 全景 → 聚焦 → 回全景 | 模块嵌套、调用链、系统边界 | 局部始终保留全局锚点 |
| 递进因果 | 审批、重试、提醒注入、数据变换 | 每次只新增一个因果动作 |
| 前后对照 | 压缩、装配、序列化、上下文变化 | 前后对象身份和字段关系一致 |
| 并行对照 | 同步/异步、多个实例、成功/失败分支 | 明确是否真实并发和汇合条件 |
| 先结果后回溯 | 先展示用户看到的结果，再解释内部原因 | 回溯路径要回到同一个关联 ID |
| 横切叠加 | EventBus、Trace、权限等观察/控制机制 | 叠加线不能冒充主调用线 |

“非线性”不是随意跳跃。每次换视角都要保留至少一个稳定锚点：任务 ID、对象身份、全景位置、章节路径或同一份载荷。没有锚点时宁可用线性片段。

## 资料变化与修订

文档补充或用户调整重点后，先检查它是否改变参与者、依赖顺序、状态所有权、条件、不变量或已有结论。改变因果则更新相应局部及全景关系；仅新增可回查的实现入口则补笔记；其余已核实内容复用。修订详略时保留当前镜头的必要技术层级和核心结论，再调整方法行、字段或解释量，避免改动一项把其他已达成的理解条件一起丢掉。

## 产物与停止条件

建议在目标项目的 .project-to-video/research/ 和 planning/ 中保留：system-map.md、flow-inventory.md、evidence.md、narrative-decision.md 和可选的 coverage-matrix.md。简单项目可以合并文件，但要保留同样的信息。

进入分镜前，应能用不超过几句话回答：项目核心承诺是什么、锚点主线是什么、两条支撑线解决什么疑问、每条线的关键分支是什么、哪些事实仍不确定。回答不了时继续探索，不用动画掩盖空白。
